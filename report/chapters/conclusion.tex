\chapter{Conclusion}
\label{ch:conclusion}

\section{What Was Achieved}

QLens set out to answer one practical question: can a person who only owns a messy spreadsheet be taken, step by step and with every step explained, to a verified third normal form database? The implemented system shows that the answer is yes for the class of data it targets, namely a single flat table of up to 60 columns and a few thousand rows.

The pipeline that exists today runs from a CSV or XLSX upload to a proposed 3NF design. Type inference, candidate-key search and functional-dependency discovery all execute inside PostgreSQL, through the PL/pgSQL functions \code{qlens.check\_fd} and \code{qlens.is\_unique}, so the data never leaves the database to be analysed. On the bundled coaching-centre fee register (3,000 rows, 8 columns) the complete analysis takes about 0.3 seconds. Near-duplicate detection uses \code{pg\_trgm} with a GIN index on a temporary table and handles 5,000 distinct values in about one second~\cite{pgtrgm}. The planted errors in that sample, eight rows with variant spellings of four student names and five rows carrying a teacher's superseded phone number, are found, shown to the user, and repaired with an audit trail in \tbl{dataset\_fixes}.

The normalisation step rests on a small, separately tested algebra module: attribute closure, minimal cover and Bernstein's synthesis~\cite{bernstein1976}, with a lossless-join relation added whenever no synthesised relation contains a key. It was checked by property-based tests over thousands of random dependency sets rather than by a handful of hand-picked examples. For the fee register the result after cleanup is the expected four-table design: \code{students}, \code{batches}, \code{teachers} and a slim \code{fee\_register} that carries only the student reference, month, amount and payment mode, with a composite unique key on student and month.

Around this pipeline sits a metadata schema of 22 tables that makes use of most of what a course on relational systems introduces: generated columns, \code{CHECK} constraints that encode business rules (for example, an applied proposal must have passed its lossless check), partial unique indexes that allow at most one draft and one applied proposal per dataset, triggers for timestamps and for recording query runs, and views built with window functions for slow-query and trend reporting. Each workspace is isolated by its own \code{LOGIN} role and its own pair of schemas, which is the mechanism later used to sandbox user queries. The backend carries 212 automated tests in its latest full run, the frontend has its own passing suite, and the interface has a pure-black dark theme and a light theme.

\section{What Was Learnt}

Several textbook ideas looked different once they had to run against real data.

\paragraph{Dependencies are statistical before they are logical.}
Theory defines a functional dependency as holding or not holding. A spreadsheet of 3,000 rows never behaves that way: the dependency \fd{student\_phone}{student\_name} fails in exactly eight rows because of typos. Recording \code{violating\_rows} and a generated \code{violation\_ratio} for every candidate, and letting the user decide whether a near-miss is a real rule with dirty data or a coincidence, turned out to be the central design decision of the analysis stage.

\paragraph{Normalisation needs clean data first.}
Bernstein's algorithm is only correct for the dependencies it is given. If the dependency from phone to name is rejected because of eight misspelt rows, the design silently keeps a redundant column. The order in the product (profile, find duplicates, repair, then analyse again) follows from this and is not a matter of taste.

\paragraph{Let the database do set-oriented work.}
Checking a dependency is a single \code{GROUP BY ... HAVING count(DISTINCT ...) > 1}. Running it inside the server avoided shipping rows to Python, and with a bound on the size of the left-hand side the number of candidate checks stays small enough to finish in a fraction of a second.

\paragraph{Constraints are documentation that executes.}
Encoding rules as \code{CHECK}, \code{UNIQUE} and partial indexes caught several of our own mistakes during development, long before any application code could have hidden them. The index comments in the DDL, each naming the query it serves, also made it simple to decide what \emph{not} to index.

\paragraph{Lossless-join is a testable property.}
The theorem that a Bernstein decomposition is lossless becomes, in practice, a query: rebuild the join of the new tables and compare it with the staged data using \code{EXCEPT ALL} in both directions. Using the multiset form matters, because plain \code{EXCEPT} would hide duplicate rows that the decomposition might have lost or multiplied.

\section{Limitations}

We prefer to state the boundaries of the present work plainly.

\begin{itemize}
  \item \textbf{Build status.} The apply step (creating the normalised tables in one transaction and running the lossless check), the design canvas and the query sandbox interface were still being finished when this report was written. The performance lab, the step-through visualiser and the English-language assistant are designed, and the metadata tables for them exist, but they are not yet implemented.
  \item \textbf{Bounded dependency search.} Left-hand sides are limited to at most two columns, and candidate keys to at most three. Real tables can have dependencies with three determining columns; these are not found. The bound keeps the search cheap in practice but is a deliberate loss of completeness.
  \item \textbf{Heuristics for noise.} Deciding which approximate dependencies deserve to be shown relies on thresholds on the violation ratio and on the number of repeated groups. A column with nearly unique values determines almost everything trivially, and such results are filtered out by rule, not by principle. On unusual data these rules may hide a real dependency or surface a spurious one, which is why the user always has the final say.
  \item \textbf{Single table, bounded size.} QLens normalises one flat table at a time. Multi-sheet workbooks, multivalued dependencies (4NF) and join dependencies (5NF) are outside its scope, and the target is thousands of rows rather than millions.
  \item \textbf{Fuzzy matching is not understanding.} Trigram similarity finds spellings that look alike; it cannot know that two distinct people share a name. Every merge is therefore a proposal with a confidence label and is recorded so that it can be audited.
  \item \textbf{Evidence of effectiveness.} The numbers in this report come from three synthetic datasets with planted problems and from automated tests. No study with real users has been carried out.
\end{itemize}

\section{Future Work}

\paragraph{Design canvas with a validated assistant.}
The next milestone is an interactive entity--relationship canvas where the user can rename tables, move a column, or split a table and see the effect on keys and foreign keys immediately. On top of it we plan an assistant powered by the Gemini API that accepts instructions such as ``separate the teacher details''. The assistant would not write to the database. It would emit structured tool calls (rename, move column, add key), each of which is validated against the same constraint rules as manual edits, shown as a diff, and applied only after confirmation. Invalid or lossy requests are rejected by the validator and are never left to the model's judgement.

\paragraph{Performance lab.}
The \tbl{query\_runs} table already records duration and row counts, and \tbl{v\_slow\_queries} ranks the slowest statements. The lab will present \code{EXPLAIN (ANALYZE, BUFFERS)} output as a tree, compare plans before and after an index is added, and suggest indexes from the filters and joins that actually occur in the history.

\paragraph{Step-through visualiser.}
A teaching mode that evaluates a query one operator at a time (scan, filter, join, group, project) and shows the intermediate relation after each, so that a learner can connect the SQL text with relational algebra.

\paragraph{Larger dependency search and 4NF.}
Allowing a wider left-hand side with pruning by minimality, sampling for large tables, and detecting multivalued dependencies would extend the design stage towards BCNF and 4NF.

\paragraph{Deployment.}
QLens currently runs locally against a private PostgreSQL cluster. A hosted version would need per-tenant resource limits, connection pooling and scheduled clean-up of idle workspace schemas, all of which the per-workspace role design was chosen to make possible.
