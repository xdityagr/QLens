\section{Design Goals}
\label{sec:goals}

\begin{enumerate}[label=G\arabic*.]
  \item \textbf{Correct by construction, verified on data.} Designs are 3NF and lossless by the
  algorithm, and every apply re-checks losslessness on the real rows before committing.
  \item \textbf{SQL in plain sight.} No ORM: constraints, PL/pgSQL, triggers, views, dynamic SQL and
  catalog queries are hand-written, and the generated SQL is shown to the user.
  \item \textbf{Work where the data is.} Profiling, dependency checks and duplicate search run inside
  PostgreSQL; only the set algebra of synthesis runs in Python.
  \item \textbf{Isolation by privilege.} A user's query reaches only its own workspace because the
  database role lacks the privileges, not because the application filters text.
  \item \textbf{Non-destructive and auditable.} The raw import is never modified; every repair is a
  logged, transactional edit of a separate staging copy.
\end{enumerate}

\section{System Architecture}
\label{sec:architecture}

\InputIfFileExists{figures/architecture}{}{}

QLens is a three-tier web application whose bottom tier does unusually much work
(\cref{fig:architecture}). The \emph{client} is a React 19 and TypeScript single-page application
\cite{react} with React Flow diagrams and a CodeMirror SQL editor; it talks JSON to \code{/api/*} with the
session in an \code{httpOnly} cookie. The \emph{application tier} is FastAPI on Python 3.13
\cite{fastapi} with psycopg~3 \cite{psycopg} and pglast \cite{pglast}; each request runs in one transaction
on a pooled connection as the owning role \code{qlens\_app}, committed before the response is sent. The
\emph{data tier} is a private PostgreSQL 18 cluster \cite{postgres18docs} holding the \code{qlens}
metadata schema and, per workspace, the schemas \code{ws\_<id>\_src} (\code{\_raw}, never edited, and
\code{\_staging}, typed and cleaned), \code{ws\_<id>} (the generated tables) and \code{ws\_<id>\_lab}
(\stplan), plus one login role \code{qlens\_ws\_<id>} (\cref{sec:db-logic}).

\section{Detailed Design Methodologies}
\label{sec:detailed}

The design has two halves: the \emph{database design} of QLens itself and of the databases it generates
(\cref{sec:db-er} to \cref{sec:db-sql}), and the \emph{methods} that turn a sheet into such a database
(\cref{sec:design-discovery} onwards).

\subsection{Conceptual Design: ER Diagram}
\label{sec:db-er}
\label{sec:design-metadata}

QLens records everything it knows in the \code{qlens} schema: 22 tables plus a migrations log
(\cref{fig:er}). Users own workspaces; a workspace has at most one dataset; a dataset has columns,
candidate keys, functional dependencies, duplicate groups and a log of fixes; designs are proposals with
their tables, columns and unique keys; and the query side records saved queries, runs, plans and index
experiments. Multi-column keys and dependency left-hand sides are many-to-many relationships between a
key (or dependency) and dataset columns, resolved by junction tables.

\subsection{Normalization of the Schema}
\label{sec:db-normal}

Each table describes one kind of thing and every non-key attribute depends on the whole key and nothing
else, so the schema is in BCNF apart from the deliberate cases below; in particular there are no
transitive dependencies through non-key attributes. Lists are never stored in a column when they are
facts in their own right: the columns of a candidate key, the left-hand side of a dependency and the
columns of a unique key each live in a junction table, so ``which dependencies use column $c$?'' is an
indexed join, not a string search. (\code{sample\_values} and \code{index\_experiments.columns} are
arrays because they are display values, never queried by element.) Three denormalizations are
deliberate. \code{dataset\_id} is stored next to \code{column\_id} in \tbl{duplicate\_groups},
\tbl{dataset\_fixes} and \tbl{functional\_dependencies} although it follows from the column, so that the
Analyze page filters by dataset without a join; \code{workspace\_id} in \tbl{explain\_snapshots} likewise saves a join through \tbl{query\_runs}
(and lets a plan without a run belong to a workspace). Derived values such as
\code{is\_exact}, \code{violation\_ratio} and \code{speedup} are \code{GENERATED ALWAYS AS (\dots) STORED},
so the redundancy can never become an anomaly: the database recomputes them on every write.
\code{run\_count} and \code{last\_run\_at} of a saved query are maintained by a trigger for the same reason.

\subsection{Triggers, Views, Functions and Roles}
\label{sec:db-logic}

\paragraph{Triggers.} \code{touch\_updated\_at} is a \code{BEFORE UPDATE} row trigger on workspaces,
datasets and saved queries; it uses \code{clock\_timestamp()} because \code{now()} is frozen for the whole
transaction. \code{record\_query\_run} (\cref{lst:trigger}) keeps a saved query's counters in step with its
successful runs; the \code{WHEN} clause filters before the function is even called.

\begin{lstlisting}[caption={[Run-recording trigger]AFTER INSERT trigger on \code{query\_runs} (\code{002\_logic.sql})},label={lst:trigger}]
CREATE FUNCTION qlens.record_query_run() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    UPDATE qlens.saved_queries
       SET run_count = run_count + 1, last_run_at = NEW.created_at,
           last_duration_ms = NEW.duration_ms
     WHERE id = NEW.saved_query_id;
    RETURN NULL;   -- AFTER trigger: return value is ignored
END $$;
CREATE TRIGGER query_runs_record AFTER INSERT ON qlens.query_runs
    FOR EACH ROW WHEN (NEW.saved_query_id IS NOT NULL AND NEW.status = 'ok')
    EXECUTE FUNCTION qlens.record_query_run();
\end{lstlisting}

\paragraph{Views.} \code{v\_workspace\_summary} gives the dashboard one row per workspace using two
\code{LEFT JOIN LATERAL} aggregates (an aggregate without \code{GROUP BY} always returns a row, so empty
workspaces are kept) and \code{GREATEST} over three timestamps. \code{v\_slow\_queries} keeps the runs at or
above their workspace's 90th percentile, computed with \code{percentile\_cont(0.9) WITHIN GROUP (ORDER BY
duration\_ms)}. \code{v\_saved\_query\_trend} numbers each saved query's runs and adds the previous duration
and a five-run moving average with the window functions \code{row\_number()}, \code{lag()} and
\code{avg() OVER (\dots{} ROWS BETWEEN 4 PRECEDING AND CURRENT ROW)}.

\paragraph{PL/pgSQL functions.} \code{try\_date(text)} parses ISO and day-first dates and returns NULL
instead of raising, so type inference can test every value; \code{check\_fd} (\cref{lst:checkfd}) and
\code{is\_unique} measure dependencies and keys with dynamic SQL in which identifiers pass only through
\code{format('\%I')}.

\paragraph{Roles and privileges.} Creating a workspace runs, in the same transaction,
\code{CREATE ROLE qlens\_ws\_<id> LOGIN PASSWORD \dots{} NOINHERIT CONNECTION LIMIT 3}, then
\code{ALTER ROLE \dots{} SET} \code{default\_transaction\_read\_only = on}, \code{statement\_timeout = '5s'},
\code{idle\_in\_transaction\_session\_timeout = '10s'} and the \code{search\_path}, and for each of its schemas
\code{GRANT USAGE ON SCHEMA}, \code{GRANT SELECT ON ALL TABLES IN SCHEMA} and \code{ALTER DEFAULT PRIVILEGES
\dots{} GRANT SELECT ON TABLES}. The role gets nothing on \code{qlens} or on any other workspace. Its
password is an HMAC of the workspace id under the server secret, so it is never stored, and deleting the
workspace runs \code{DROP OWNED BY} and \code{DROP ROLE}.

\Cref{lst:trgm} is the core of the near-duplicate search (\code{cleanup.py}). The \code{MATERIALIZED} CTE
forces the index-backed \code{\%} join to run first; the outer filters then drop pairs whose digits differ
and pairs of equally frequent values.

\begin{lstlisting}[caption={[Trigram near-duplicate search]Near-duplicate search with \code{pg\_trgm} over a GIN index (from \code{cleanup.py})},label={lst:trgm}]
CREATE INDEX ON pg_temp._qlens_vals USING gin (val gin_trgm_ops);
SELECT set_config('pg_trgm.similarity_threshold', '0.5', true);
WITH m AS MATERIALIZED (SELECT a.val AS a, a.n AS an, b.val AS b, b.n AS bn
                        FROM pg_temp._qlens_vals a JOIN pg_temp._qlens_vals b
                        ON a.val % b.val AND a.val < b.val)
SELECT a, an, b, bn, similarity(a, b) AS sim FROM m
WHERE regexp_replace(a, '[^0-9]', '', 'g') = regexp_replace(b, '[^0-9]', '', 'g')
  AND least(an, bn) <= greatest(an, bn) * 0.333;
\end{lstlisting}

\subsection{Dependency Discovery and Cleaning}
\label{sec:design-discovery}
\label{sec:design-cleanup}

\InputIfFileExists{figures/pipeline}{}{}

\Cref{fig:pipeline} shows the pipeline from upload to apply. \code{qlens.check\_fd} (\cref{lst:checkfd})
returns, for $X \rightarrow A$, the rows that would have to change for the dependency to hold: per
$X$-group, every row except those with the most frequent $A$, the $g_3$ measure of approximate
dependencies \cite{kivinen1995}. A dependency is exact at 0, approximate up to 2\% of rows, and needs at
least two repeated $X$-groups. Keys are tested with \code{is\_unique} on 1--3 columns after pruning by the
profile (no NULLs; the product of distinct counts must reach the row count). Measures are never
determinants, a pair is dropped when one of its columns already determines the target, an approximate
dependency explained through an exact one is reported once at its root, and implied dependencies are
flagged \emph{derived}. On the fee register six core dependencies remain, two approximate (8 and 5 rows).

\begin{lstlisting}[caption={[Dependency check]\code{qlens.check\_fd}: measuring a dependency with dynamic SQL (\code{004\_analysis.sql})},label={lst:checkfd}]
CREATE FUNCTION qlens.check_fd(p_schema text, p_table text, p_lhs text[], p_rhs text)
RETURNS TABLE (row_count bigint, lhs_values bigint, repeated_groups bigint, violating_rows bigint)
LANGUAGE plpgsql STABLE AS $$
DECLARE
    t   text := format('%I.%I', p_schema, p_table);
    lhs text;
BEGIN
    SELECT string_agg(format('%I', c), ', ') INTO lhs FROM unnest(p_lhs) AS c;
    RETURN QUERY EXECUTE format(
        'WITH c AS (SELECT %1$s, %2$I, count(*) AS cnt FROM %3$s GROUP BY %1$s, %2$I), '
        '     g AS (SELECT %1$s, sum(cnt) AS n, max(cnt) AS keep FROM c GROUP BY %1$s) '
        'SELECT (SELECT count(*) FROM %3$s), count(*), count(*) FILTER (WHERE n >= 2), '
        '       coalesce(sum(n - keep), 0)::bigint FROM g',
        lhs, p_rhs, t);
END;
$$;
\end{lstlisting}

Cleaning edits only \code{\_staging}. Spellings equal after lower-casing and collapsing spaces are certain
duplicates; probable typos come from \cref{lst:trgm} \cite{angell1983}, clustered with union--find. Each
approximate dependency lists its conflicting groups with the most frequent value as the suggestion (the
minimal repair under $g_3$). Every merge or fix is one transactional \code{UPDATE}, logged in
\tbl{dataset\_fixes} and followed by re-profiling; ``accept all'' does all of them and re-analyzes.

\subsection{3NF Synthesis}
\label{sec:design-3nf}

The design is built from exactly the dependencies the user sees: exact, accepted and not derived.
Closure, minimal cover and synthesis (\cref{alg:bernstein}) are set algebra in Python: $X \rightarrow A$
follows from $F$ iff $A \in X^{+}$ \cite{armstrong1974}; groups with equivalent determinants are merged and
Bernstein's step 5 prunes what the equivalences make redundant \cite{bernstein1976}. Synthesis alone is
lossless only if some relation contains a key of the whole table \cite{biskup1979}, so QLens designates as
\emph{fact} the relation that contains every undetermined attribute and determines everything, or adds
one built from a key of the dependencies. Joining outward from the fact, each join is on a key of the
relation joined, so rows are neither added nor lost; 900 randomized cases are checked against a chase-based
lossless test \cite{aho1979} and a brute-force 3NF test.

\subsection{Generated Database and Apply}
\label{sec:design-apply}

\stdone{} Each synthesized relation becomes a table with \code{id bigint GENERATED ALWAYS AS IDENTITY
PRIMARY KEY}. Its determinant and equivalent determinants become \code{UNIQUE NULLS NOT DISTINCT}
constraints, so an empty \emph{Teacher} cell is one teacher stored once. A relation that contains another
entity's natural key stores a foreign key \code{<entity>\_id ... ON DELETE RESTRICT} instead, \code{NOT
NULL} when the replaced columns had no empty cells. Tables are named from their determinant, explained in
plain English and renamable while the design is a draft (409 \code{proposal\_not\_draft} afterwards).
\Cref{fig:er-generated} is the result for the fee register.

\InputIfFileExists{figures/er-generated}{}{}

The script is generated in foreign-key order: entity loads are \code{INSERT \dots{} SELECT DISTINCT} from
\code{\_staging}; foreign keys are looked up by natural key with \code{=} where the key has no NULLs (so a
hash join is possible) and \code{IS NOT DISTINCT FROM} otherwise; the fact keeps every row; and the view
\code{original\_sheet} joins everything back. Apply runs it in one transaction: lock the draft
(\code{FOR UPDATE}), drop and recreate the workspace schema, execute, and run \cref{lst:lossless}. A
non-zero count raises 409 \code{lossless\_check\_failed} with up to five differing rows and PostgreSQL rolls
everything back. Otherwise the old applied design becomes \emph{superseded} before the new one becomes
\emph{applied} (the partial unique indexes allow only one), and the new tables are \code{ANALYZE}d.

\begin{lstlisting}[caption={[Lossless check]Lossless check generated for the fee register (\code{cols} abbreviates the eight sheet columns)},label={lst:lossless}]
SELECT (SELECT count(*) FROM ws_20_src._staging)  AS staging_rows,
       (SELECT count(*) FROM ws_20.original_sheet) AS reconstructed_rows,
       (SELECT count(*) FROM (SELECT cols FROM ws_20.original_sheet
                              EXCEPT ALL SELECT cols FROM ws_20_src._staging) d) AS extra_rows,
       (SELECT count(*) FROM (SELECT cols FROM ws_20_src._staging
                              EXCEPT ALL SELECT cols FROM ws_20.original_sheet) d) AS missing_rows;
\end{lstlisting}

\code{EXCEPT ALL} compares multisets, so a lost or duplicated copy of a repeated row is counted, and both
directions are needed because $A$ \code{EXCEPT ALL} $B$ is empty whenever $A \subseteq B$. On the cleaned
fee register all 3{,}000 rows come back exactly; tests also cover forced failures, reserved-word headers,
empty determinants, the other samples and random sheets (a 400-seed run passed throughout).

\paragraph{Example queries.} \Cref{lst:examples} shows queries a user runs on the generated database in
the Query screen; on the applied fee register they return 19 students unpaid for October, 6 batches with
more than 25 unpaid months (JEE Evening, Mr.\ Gupta, first with Rs.~12{,}75{,}800 collected) and one
ranked row for each of the 300 students.

\begin{lstlisting}[caption={[Example queries]Example queries on the generated fee-register database (runnable in the Query screen)},label={lst:examples}]
-- 1. Who has not paid for October? (joins)
SELECT s.student_name, s.student_phone, b.batch
FROM fee_register f JOIN students s ON s.id = f.student_id
                    JOIN batches  b ON b.id = s.batch_id
WHERE f.month = 'Oct' AND f.fee_paid = 0 ORDER BY b.batch, s.student_name;
-- 2. Collection per batch and teacher, only batches with many unpaid months
SELECT b.batch, t.teacher, sum(f.fee_paid) AS collected,
       count(*) FILTER (WHERE f.fee_paid = 0) AS unpaid
FROM fee_register f JOIN students s ON s.id = f.student_id
     JOIN batches b ON b.id = s.batch_id JOIN teachers t ON t.id = b.teacher_id
GROUP BY b.batch, t.teacher
HAVING count(*) FILTER (WHERE f.fee_paid = 0) > 25 ORDER BY collected DESC;
-- 3. Rank students within their batch by total paid (window function)
SELECT batch, student_name, total,
       rank() OVER (PARTITION BY batch ORDER BY total DESC) AS rank_in_batch
FROM (SELECT b.batch, s.student_name, sum(f.fee_paid) AS total
      FROM fee_register f JOIN students s ON s.id = f.student_id
           JOIN batches b ON b.id = s.batch_id
      GROUP BY b.batch, s.student_name) t
ORDER BY batch, rank_in_batch;
\end{lstlisting}

\subsection{Query Sandbox}
\label{sec:design-sandbox}

\InputIfFileExists{figures/sequence-query}{}{}

\stdone{} A user query never runs on the application's pooled connection (\cref{fig:seq-query}). The
validator parses it with pglast, the PostgreSQL parser itself, walking the tree iteratively with a token
cap: it must be exactly one \code{SELECT} (set operations allowed), without \code{INTO}, locking clauses or
data-modifying CTEs, and without functions on a denylist (\code{set\_config}, \code{pg\_read\_file},
\code{dblink}, \code{query\_to\_xml} and others). The validator gives friendly errors but is not the
security boundary. The runner opens a fresh login as \code{qlens\_ws\_<id>}, starts a \code{READ ONLY}
transaction, sets a local \code{statement\_timeout} of at most 5\,s, declares a cursor for the query with
the extended protocol (which refuses a second statement) and fetches 1{,}001 rows, so that a 1{,}000-row cap
and a \emph{truncated} flag need no full materialization; it always rolls back. A timeout is reported as
SQLSTATE 57014. Every run, failed or not, is then inserted into \tbl{query\_runs}, where the trigger of
\cref{lst:trigger} updates the saved query.
