\chapter{System Design}
\label{ch:design}

\section{Design Goals}
\label{sec:goals}

\begin{enumerate}[label=G\arabic*.]
  \item \textbf{Correct design.} Tables must be in 3NF, lossless and dependency-preserving, and the
  lossless join is checked again on the real rows before the tables are kept.
  \item \textbf{SQL in plain sight.} All SQL is hand-written (no code generator hides it), and the user
  can read the SQL that QLens runs.
  \item \textbf{Use the database.} Counting, grouping and checking are done by SQL inside PostgreSQL.
  \item \textbf{Safe queries.} A user's query can read only that user's workspace, because its database
  user has no other privileges.
  \item \textbf{Nothing is lost.} The original sheet is never changed, and every fix is logged.
\end{enumerate}

\section{System Architecture}
\label{sec:architecture}

\InputIfFileExists{figures/architecture}{}{}

QLens has three tiers (\cref{fig:architecture}):
\begin{enumerate}
  \item \textbf{Browser.} The screens are web pages written in React \cite{react}. They send requests to
  the server and show the results.
  \item \textbf{Application server.} A FastAPI program in Python \cite{fastapi} receives each request,
  runs the needed SQL through the psycopg library \cite{psycopg}, and returns the answer. Each request runs
  as one transaction.
  \item \textbf{Database server.} PostgreSQL 18 \cite{postgres18docs} holds two kinds of schema (a
  \emph{schema} is a named group of tables inside one database). The \code{qlens} schema holds QLens's own
  data. Each workspace gets its own schemas: \code{ws\_<id>\_src} keeps the uploaded sheet (an untouched
  copy \code{\_raw} and a typed, cleaned copy \code{\_staging}), and \code{ws\_<id>} receives the
  generated tables.
\end{enumerate}

The application uses two database users. The owner user \code{qlens\_app} does QLens's own work. For
every workspace there is also a restricted user \code{qlens\_ws\_<id>} that may only \emph{read} that
workspace's schemas; all queries typed by people run as this user (\cref{sec:design-sandbox}).

\section{Detailed Design Methodologies}
\label{sec:detailed}

This section first describes the database design of QLens itself (ER model, relational schema,
constraints, SQL), and then the method QLens uses to design a database for the user, following the fee
register as a worked example.

\subsection{ER Model of QLens}
\label{sec:db-er}

\Cref{fig:er} is the ER diagram of the data QLens stores. A \emph{User} owns many \emph{Workspaces}; a
workspace holds one \emph{Dataset} (the imported sheet), which has many \emph{Columns}. For a dataset
QLens finds \emph{Functional Dependencies} and \emph{Candidate Keys}; both are linked to columns by M\,:\,N
relationships, because one dependency can have several columns on its left-hand side (LHS) and one
column can appear in many dependencies. A dataset gets \emph{Schema Proposals} (designs), which contain
\emph{Proposed Tables} and \emph{Proposed Columns}; a proposed column may refer to another proposed table
(it becomes a foreign key). On the query side, a workspace has \emph{Saved Queries} and \emph{Query
Runs}, and a \emph{Row Change} log of edits made in the Data screen (\stwip). Some attributes are
\emph{derived attributes}: for example a dependency's \code{is\_exact} is derived from
\code{violating\_rows = 0}, and PostgreSQL computes it automatically.

\subsection{ER Diagram to Relational Schema}
\label{sec:db-schema}

The ER diagram was converted into tables with the standard rules \cite{silberschatz2019}:
\begin{enumerate}
  \item Each entity set becomes a table; its key \code{id} becomes the primary key.
  \item A 1\,:\,N relationship becomes a foreign key on the N side (e.g.\ \code{workspaces.owner\_id}
  refers to \code{users.id}).
  \item A 1\,:\,1 relationship becomes a foreign key with a \code{UNIQUE} constraint (e.g.\
  \code{datasets.workspace\_id}).
  \item An M\,:\,N relationship becomes its own table whose primary key is the pair of foreign keys
  (\code{fd\_lhs\_columns}, \code{candidate\_key\_columns}, \code{proposed\_unique\_key\_columns}).
\end{enumerate}

\label{sec:db-keys}

\code{UNIQUE} constraints, for example \code{users(email)}, \code{workspaces(owner\_id, name)} and
\code{saved\_queries(workspace\_id, title)}. \Cref{tab:keys} lists the main foreign keys.

\paragraph{Integrity constraints.} The database itself rejects wrong data:
\begin{itemize}
  \item \textbf{NOT NULL} on every column that must always have a value.
  \item \textbf{CHECK} constraints for business rules, for example
  \code{CHECK (status <> 'applied' OR lossless\_ok IS TRUE)}: a design can be marked \emph{applied}
  only if its lossless-join check passed; and \code{CHECK (status IN ('draft', 'applied',
  'superseded'))} for allowed values.
  \item \textbf{UNIQUE} constraints that allow only one draft and one applied design per dataset.
  \item \textbf{Referential integrity}: \code{ON DELETE CASCADE} deletes the children with their parent,
  so deleting a user leaves no orphan rows; \code{SET NULL} keeps the run history when a saved query is
  deleted.
\end{itemize}

\subsection{Normalization of the QLens Schema}
\label{sec:db-normal}

In each table every non-key attribute depends on the key, the whole key, and nothing but the key, so
the tables are in 3NF (and in BCNF, because every determinant is a key). Two points show this:
\begin{enumerate}
  \item \textbf{No repeating groups.} The columns of a dependency's left-hand side are not stored as a
  list in one cell; they are rows of the table \code{fd\_lhs\_columns}. The same holds for the columns of
  a candidate key.
  \item \textbf{Deliberate, controlled redundancy.} \code{dataset\_id} is stored in
  \code{functional\_dependencies} even though it can be found through the column; this saves a join on
  the Analyze screen. Derived attributes such as \code{is\_exact} are computed by the database, and a
  saved query's \code{run\_count} is maintained by a trigger, so these copies can never disagree.
\end{enumerate}

\paragraph{Trigger.} After a successful run of a saved query is inserted into \code{query\_runs}, this
trigger updates the saved query's counters:

\begin{lstlisting}[float=tbp,caption={[Trigger]Trigger that updates a saved query after each successful run},label={lst:trigger}]
CREATE FUNCTION qlens.record_query_run() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    UPDATE qlens.saved_queries
       SET run_count = run_count + 1, last_run_at = NEW.created_at,
           last_duration_ms = NEW.duration_ms
     WHERE id = NEW.saved_query_id;
    RETURN NULL;
END $$;
CREATE TRIGGER query_runs_record AFTER INSERT ON qlens.query_runs
    FOR EACH ROW WHEN (NEW.saved_query_id IS NOT NULL AND NEW.status = 'ok')
    EXECUTE FUNCTION qlens.record_query_run();
\end{lstlisting}

\paragraph{Stored function.} \code{check\_fd} tests whether a functional dependency $X \rightarrow A$
holds in a table. It groups the rows by $X$ and $A$, and counts how many rows would have to change for
every $X$ value to have only one $A$ value. Zero means the dependency holds exactly.

\begin{lstlisting}[float=tbp,caption={[Stored function check\_fd]Stored function that measures a functional dependency},label={lst:checkfd}]
CREATE FUNCTION qlens.check_fd(p_schema text, p_table text, p_lhs text[], p_rhs text)
RETURNS TABLE (row_count bigint, lhs_values bigint, repeated_groups bigint, violating_rows bigint)
LANGUAGE plpgsql STABLE AS $$
DECLARE
    t   text := format('%I.%I', p_schema, p_table);
    lhs text;
BEGIN
    SELECT string_agg(format('%I', c), ', ') INTO lhs FROM unnest(p_lhs) AS c;
    RETURN QUERY EXECUTE format(
        'WITH c AS (SELECT %1$s, %2$I, count(*) AS cnt FROM %3$s GROUP BY %1$s, %2$I), '
        '     g AS (SELECT %1$s, sum(cnt) AS n, max(cnt) AS keep FROM c GROUP BY %1$s) '
        'SELECT (SELECT count(*) FROM %3$s), count(*), count(*) FILTER (WHERE n >= 2), '
        '       coalesce(sum(n - keep), 0)::bigint FROM g',
        lhs, p_rhs, t);
END;
$$;
\end{lstlisting}

\paragraph{Transactions and ACID.} A \emph{transaction} is a group of statements that runs completely or
not at all. QLens relies on this:
\begin{enumerate}
  \item \textbf{Atomicity.} Applying a design creates all tables, fills them and checks them in one
  transaction. If the check fails, \code{ROLLBACK} removes everything and the old tables stay.
  \item \textbf{Consistency.} Constraints (keys, \code{CHECK}, foreign keys) are checked inside the
  transaction, so a design that breaks them is never committed.
  \item \textbf{Isolation.} Two people applying the same design cannot interfere: the design row is
  locked with \code{SELECT \dots{} FOR UPDATE}.
  \item \textbf{Durability.} After \code{COMMIT} the new tables are permanent.
\end{enumerate}

\paragraph{Indexing.} PostgreSQL's default index is a B-tree. Besides the indexes it creates for primary
keys and \code{UNIQUE} constraints, QLens adds B-tree indexes on foreign-key columns (for joins and
cascading deletes) and an index on \code{query\_runs (workspace\_id, created\_at DESC)}, which lets the
History page read the latest runs of a workspace without scanning the whole table.

\subsection{Normalization Method (Worked Example)}
\label{sec:design-3nf}

This is how QLens designs a database for the user, shown on the fee register.

\InputIfFileExists{figures/pipeline}{}{}

\paragraph{Step 1: find the functional dependencies.} A \emph{functional dependency} $X \rightarrow A$
means that rows with the same $X$ value always have the same $A$ value. QLens tests every candidate pair
with \code{check\_fd} (\cref{lst:checkfd}) and every small column set with \code{is\_unique} (a candidate
key is a minimal set of columns whose values are different in every row). For the fee register it finds
the dependencies of \cref{fig:fee-example} and the candidate key (\code{student\_name}, \code{month}).
Two dependencies hold on all but a few rows; they point to data errors.

\InputIfFileExists{figures/fee-example}{}{}

\paragraph{Step 2: clean the data.} The 8 rows with name variants (``riya sharma'') and the 5 rows with
Mr.\ Gupta's old phone number are shown to the user with a suggested fix (the most common value). Similar
spellings are found with PostgreSQL's \code{similarity()} function. Each fix is an \code{UPDATE} on the
typed copy, run in a transaction and logged. Afterwards both dependencies hold exactly.

\paragraph{Step 3: canonical cover.} The \emph{closure} $X^{+}$ of a set of columns is every column that
$X$ determines through the dependencies. Using closures, QLens removes extra columns from left-hand sides
and drops dependencies that follow from the others. This gives the \emph{canonical cover} $F_c$:
\begin{quote}\small
student\_name $\rightarrow$ student\_phone, batch \qquad student\_phone $\rightarrow$ student\_name\\
batch $\rightarrow$ teacher \qquad teacher $\rightarrow$ teacher\_phone \qquad teacher\_phone $\rightarrow$ teacher\\
student\_name, month $\rightarrow$ fee\_paid, payment\_mode \quad (from the candidate key)
\end{quote}
For example, student\_name $\rightarrow$ teacher is dropped, because it follows from student\_name
$\rightarrow$ batch and batch $\rightarrow$ teacher.

\paragraph{Step 4: 3NF decomposition.} \Cref{alg:synthesis} makes one table for each dependency of $F_c$
and removes tables contained in others:
\begin{itemize}
  \item $R_1$(student\_name, student\_phone, batch) \quad (student\_phone $\rightarrow$ student\_name fits inside $R_1$)
  \item $R_2$(batch, teacher)
  \item $R_3$(teacher, teacher\_phone) \quad (teacher\_phone $\rightarrow$ teacher fits inside $R_3$)
  \item $R_4$(student\_name, month, fee\_paid, payment\_mode) \quad (contains the candidate key)
\end{itemize}
QLens then names the tables (students, batches, teachers, fee\_register), gives each an \code{id} primary
key, keeps the natural key as \code{UNIQUE}, and replaces a column that points to another table with a
foreign key (batch $\rightarrow$ \code{batch\_id}, student\_name $\rightarrow$ \code{student\_id}).

\InputIfFileExists{figures/bernstein}{}{}

\paragraph{Step 5: dependency preservation.} Every dependency of $F_c$ lies inside one table, so each can
be checked on that table alone; for example the \code{UNIQUE(teacher)} constraint of \code{teachers}
enforces teacher $\rightarrow$ teacher\_phone. The decomposition is therefore dependency-preserving.

\paragraph{Step 6: lossless join.} A decomposition is \emph{lossless} if joining the tables gives back
exactly the original relation $r$. In relational algebra the condition is
\[ r = \Pi_{R_1}(r) \bowtie \Pi_{R_2}(r) \bowtie \Pi_{R_3}(r) \bowtie \Pi_{R_4}(r). \]
In theory this holds because $R_4$ contains a candidate key and each join is on a key of one side. QLens
also checks it on the real rows: a view \code{original\_sheet} joins the new tables back, and two set
differences must both be empty. \code{EXCEPT ALL} is SQL's set difference that also counts duplicate rows.

\begin{lstlisting}[float=tbp,caption={[Lossless-join check]Lossless-join check for the fee register (\code{cols} stands for the eight sheet columns)},label={lst:lossless}]
SELECT (SELECT count(*) FROM (SELECT cols FROM ws_20.original_sheet
                              EXCEPT ALL SELECT cols FROM ws_20_src._staging) d) AS extra_rows,
       (SELECT count(*) FROM (SELECT cols FROM ws_20_src._staging
                              EXCEPT ALL SELECT cols FROM ws_20.original_sheet) d) AS missing_rows;
\end{lstlisting}

If either count is not zero, the transaction is rolled back. On the fee register both are zero and all
3{,}000 rows come back.

\subsection{The Generated Database}
\label{sec:design-apply}

\Cref{fig:er-generated} is the ER diagram of the database QLens builds for the fee register, and
\cref{lst:ddl} is part of the DDL it generates.

\InputIfFileExists{figures/er-generated}{}{}

\begin{lstlisting}[float=tbp,caption={[Generated DDL]Part of the DDL generated for the fee register},label={lst:ddl}]
CREATE TABLE ws_20.teachers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    teacher text NOT NULL,
    teacher_phone text NOT NULL,
    CONSTRAINT teachers_teacher_key UNIQUE NULLS NOT DISTINCT (teacher),
    CONSTRAINT teachers_teacher_phone_key UNIQUE NULLS NOT DISTINCT (teacher_phone)
);
CREATE TABLE ws_20.fee_register (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    student_id bigint NOT NULL,
    month text NOT NULL,
    fee_paid bigint NOT NULL,
    payment_mode text,
    CONSTRAINT fee_register_student_id_month_key UNIQUE NULLS NOT DISTINCT (student_id, month),
    CONSTRAINT fee_register_student_id_fkey FOREIGN KEY (student_id)
        REFERENCES ws_20.students (id) ON DELETE RESTRICT
);
INSERT INTO ws_20.teachers (teacher, teacher_phone)
SELECT DISTINCT s.teacher, s.teacher_phone FROM ws_20_src._staging s ORDER BY 1, 2;
\end{lstlisting}

\code{UNIQUE NULLS NOT DISTINCT} treats an empty value as one value, so a missing teacher is stored once.
\code{ON DELETE RESTRICT} stops a student from being deleted while fee records still refer to them.

\paragraph{Example queries.} \Cref{lst:examples} shows queries a user can run on the new tables in the
Query screen. On the sample they return 19 students who did not pay for October, 6 batches with more
than 25 unpaid months (the first is JEE Evening of Mr.\ Gupta, with Rs.~12{,}75{,}800 collected) and 124
students who never missed a payment.

\begin{lstlisting}[float=tbp,caption={[Example queries]Example queries on the generated database (join, aggregation, subquery)},label={lst:examples}]
-- 1. Join: who has not paid for October?
SELECT s.student_name, s.student_phone, b.batch
FROM fee_register f JOIN students s ON s.id = f.student_id
                    JOIN batches  b ON b.id = s.batch_id
WHERE f.month = 'Oct' AND f.fee_paid = 0;
-- 2. Aggregation with GROUP BY and HAVING: collection per batch and teacher
SELECT b.batch, t.teacher, sum(f.fee_paid) AS collected,
       count(*) FILTER (WHERE f.fee_paid = 0) AS unpaid
FROM fee_register f JOIN students s ON s.id = f.student_id
     JOIN batches b ON b.id = s.batch_id JOIN teachers t ON t.id = b.teacher_id
GROUP BY b.batch, t.teacher
HAVING count(*) FILTER (WHERE f.fee_paid = 0) > 25 ORDER BY collected DESC;
-- 3. Subquery: students who never missed a payment
SELECT s.student_name, b.batch
FROM students s JOIN batches b ON b.id = s.batch_id
WHERE NOT EXISTS (SELECT 1 FROM fee_register f
                  WHERE f.student_id = s.id AND f.fee_paid = 0);
\end{lstlisting}

\subsection{Query Screen and Security}
\label{sec:design-sandbox}

\InputIfFileExists{figures/sequence-query}{}{}

Users can type any SQL, so the query screen has to be safe. QLens uses database security (DCL) for
this:
\begin{enumerate}
  \item When a workspace is created, QLens runs \code{CREATE ROLE qlens\_ws\_<id> LOGIN \dots{}} and grants
  it only \code{USAGE} and \code{SELECT} on that workspace's schemas. It gets nothing on \code{qlens} or on
  other workspaces, so \code{SELECT * FROM qlens.users} fails with ``permission denied''.
  \item The role's default is a read-only transaction with a 5-second statement time limit.
  \item Before running, QLens checks with the PostgreSQL parser (pglast) that the text is exactly one
  \code{SELECT}.
  \item The query runs through a \emph{cursor}, which returns rows a few at a time. QLens fetches 1{,}001
  rows: if the 1{,}001st exists, the result is marked as cut at 1{,}000 rows.
  \item Every run, successful or not, is stored in \code{query\_runs}.
\end{enumerate}

\begin{lstlisting}[float=tbp,caption={[Cursor in the query screen]Statements the query screen runs as the restricted user},label={lst:cursor}]
BEGIN READ ONLY;
SELECT set_config('statement_timeout', '5000', true);
DECLARE qlens_run NO SCROLL CURSOR WITHOUT HOLD FOR <the user's SELECT>;
FETCH FORWARD 1001 FROM qlens_run;
ROLLBACK;
\end{lstlisting}
