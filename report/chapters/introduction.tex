\chapter{Introduction}
\label{ch:introduction}

A \emph{database management system} (DBMS) stores data in tables that are designed so that each fact is
kept once. Many small offices do not use one; they keep everything in a single spreadsheet. A coaching
institute's fee register is a typical example. Each row records one student's payment for one month:

The sheet is an \emph{unnormalized relation}: one table holds facts about students, batches, teachers
and payments together. This causes the classic problems taught in normalization \cite{silberschatz2019}:

\begin{itemize}
  \item \textbf{Update anomaly.} Mr.\ Gupta's phone number is stored on every row of every one of his
  students. When it changed, some old rows were missed, so the sheet now has two numbers for him.
  \item \textbf{Inconsistent data.} ``Riya\ \ Sharma'' and ``riya sharma'' are the same student written in
  two ways, so counts and totals are wrong.
  \item \textbf{Insertion and deletion anomalies.} A new teacher cannot be recorded until a student pays,
  and deleting the last row of a batch loses the only record of who teaches it.
\end{itemize}

The users of such sheets do not know how to design tables, and existing tools do not help: database
front-ends such as Airtable expect the user to design the tables, and chat assistants answer one question
but do not leave a correct database behind.

\textbf{QLens} solves this. It loads the sheet into PostgreSQL and finds, from the data itself, which
columns decide which other columns (\emph{functional dependencies}) and which columns identify a row
(\emph{candidate keys}). It then designs tables in third normal form, creates them with keys and
foreign keys, copies the data, and checks that no row was lost. The \textbf{objectives} were:

\begin{enumerate}[label=O\arabic*.]
  \item Find functional dependencies and keys using SQL inside the database.
  \item Produce tables in 3NF whose decomposition is lossless and dependency-preserving, and check the
  lossless join on the real rows.
  \item Keep every user's data separate using database users (roles) and \code{GRANT}.
  \item Explain every result in plain language.
\end{enumerate}

\section{Scope of the Work}
\label{sec:scope}

\paragraph{In scope.}
\begin{itemize}
  \item Import of one CSV or Excel sheet per workspace (up to 100{,}000 rows and 60 columns).
  \item Finding functional dependencies and candidate keys, and fixing data errors.
  \item Designing 3NF tables, creating them and loading the data in one transaction.
  \item A read-only SQL query screen with a history of every query.
  \item Three sample sheets with known errors: a coaching fee register, a grocery (kirana) shop's sales
  and a hostel mess register.
\end{itemize}

\paragraph{Out of scope.} Other database systems, several sheets at once, normal forms beyond 3NF
(4NF and 5NF), and changing data from the query screen. QLens runs on one computer with its own
PostgreSQL 18 server.

\paragraph{Status.} Each feature is marked \stdone{} (finished and tested), \stwip{} (partly done) or
\stplan{} (designed, not started). Nothing is described as working unless it is marked \stdone.

\section{Product Scenarios}
\label{sec:scenarios}

\paragraph{The institute owner.} \stdone{} The owner imports the fee register. QLens reports that
\emph{(Student Name, Month)} identifies every row, that Batch decides Teacher, and that Teacher decides
Teacher Phone except on 5 rows. After the owner accepts the suggested fixes, QLens proposes four tables
(students, batches, teachers and fee records) and creates them. A teacher's phone is now stored once,
and ``who has not paid for October?'' is a short SQL query.

\paragraph{The developer.} \stdone{} A developer must move an old CSV export into an application
database. QLens shows the keys and dependencies that really hold in the data and gives the
\code{CREATE TABLE} statements, ready to copy.

\paragraph{The student.} \stdone{} A student studying normalization opens the hostel sample, sees why
Room decides Hostel Block, follows the canonical cover and the 3NF design step by step, and then
practises joins and aggregate queries on the result.
