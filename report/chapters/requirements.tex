NFR-2 & Correctness & 3NF and losslessness by construction, property-tested; \code{EXCEPT ALL} check on the real rows at apply time. \\

NFR-6 & Auditability & \code{\_raw} is never edited; each fix is logged in \code{dataset\_fixes} with old value, new value and row count. \\
NFR-7 & Security & Argon2id password hashes; only SHA-256 digests of session tokens stored; every identifier quoted, every value bound. \\
NFR-8 & Usability & Plain-English findings, light and pure-black themes, motion that respects reduced-motion settings. \\
\bottomrule
\end{tabularx}
\end{table}

A text filter such as ``the statement must start with \code{SELECT}'' is easily bypassed with a
comment, a CTE or a function that writes. NFR-1 is therefore met by layers that fail independently:
privileges, a read-only transaction, a timeout and a row cap, all enforced by PostgreSQL itself
\cite{postgres18docs}.

\paragraph{Detailed flow of UC-5.} \emph{Precondition:} a draft proposal exists for an analyzed dataset.
\emph{Main flow:} the user presses Apply; the server locks the draft, drops and recreates the workspace's
main schema, creates and loads the tables, builds the \code{original\_sheet} view and runs the lossless
check; on success the proposal and dataset become \emph{applied} and the tables are analyzed.
\emph{Alternative:} if the check finds a difference, the server answers 409 with up to five differing
rows and the transaction is rolled back, so the previous tables and statuses are untouched.

\section{Other Software Engineering Methodologies}
\label{sec:methodologies}

\paragraph{Iterative, test-driven delivery.} The system was built in thin vertical increments in the
order of value: database foundation and accounts, then import, discovery, clean-up, synthesis, proposal
and apply, then querying. Each increment started from failing tests \cite{beck2002} and was followed by
a review whose findings became regression tests; for example, a randomized test showed that plain
synthesis without a key relation was lossy in 74 of 3{,}000 random cases, which led to the key step of
\cref{alg:bernstein}. The schema is managed by numbered SQL migrations applied by a small runner, and
the test database is rebuilt from them at the start of every session.

\paragraph{Test results.} \Cref{tab:tests} summarizes the suites. Database tests run against a real
PostgreSQL 18 instance, because the central logic lives in SQL and cannot be meaningfully mocked.
