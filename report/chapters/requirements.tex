\chapter{Requirement Analysis}
\label{ch:requirements}

This chapter fixes what QLens must do and how well it must do it. The requirements come from the problem described in the introduction: a small business keeps its records in one wide spreadsheet, and the same facts are typed many times with small variations. The target users are not database administrators. They are a coaching-centre owner, a shop keeper or a hostel manager who can read a table but has never written a \code{CREATE TABLE} statement. Each requirement below is therefore written from the point of view of what such a person must be able to do, and each carries a status that reflects the state of the implementation at the time of writing: \stdone{} means built and covered by automated tests, \stwip{} means partly built, and \stplan{} means designed but not yet implemented.

\section{Functional Requirements}
\label{sec:functional}

The functional requirements follow the pipeline of \cref{fig:pipeline}: a sheet enters the system, is analysed in SQL, is proposed as a normalised design, is applied, and is then queried. Requirements FR-1 to FR-8 form the normalisation pipeline; FR-9 to FR-13 are the surrounding services that make the resulting database usable.

FR-1 & \textbf{Import.} Accept CSV and XLSX files, detect the header row and delimiter, and stage the raw cells in a per-workspace source schema without losing any row. & \stdone \\
FR-2 & \textbf{Type inference.} Infer a SQL type for every column (\code{integer}, \code{numeric}, \code{date}, \code{boolean}, \code{text}) by testing the data in SQL, including day-first dates such as \code{05/03/2026}, and let the user override the choice. & \stdone \\
FR-3 & \textbf{FD and key discovery.} Discover the functional dependencies that hold in the data and the candidate keys, using queries executed inside PostgreSQL rather than in application memory. & \stdone \\

FR-5 & \textbf{Inconsistency fixes.} Detect cases where a determinant maps to more than one dependent value (an old and a new phone number for the same student), let the user choose the surviving value, and record every change in an audit log. & \stdone \\
FR-6 & \textbf{3NF proposal.} Compute a minimal cover of the discovered dependencies, synthesise a third-normal-form decomposition, choose primary keys, substitute surrogate keys for composite references, name the tables and generate the DDL. & \stdone \\

FR-9 & \textbf{Sandboxed querying.} Let the user run arbitrary SELECT statements against the new tables, with write access impossible and runaway queries stopped by the database. & \stwip \\
FR-10 & \textbf{Saved queries and history.} Keep a named, versioned list of saved queries and a log of every executed statement with its duration and row count. The metadata schema and views exist; the interface is being built. & \stwip \\
FR-11 & \textbf{Performance lab.} Show \code{EXPLAIN ANALYZE} output as a plan tree, highlight the slowest nodes and suggest indexes. & \stplan \\
FR-12 & \textbf{Step-through visualiser.} Animate how a query is evaluated, clause by clause, on a small sample of the data, for teaching purposes. & \stplan \\
FR-13 & \textbf{Agentic chat.} Offer a Gemini-powered assistant that can inspect the workspace and propose, but not silently execute, schema or query changes. & \stplan \\
FR-14 & \textbf{Accounts and workspaces.} Register and log in users; give every user isolated workspaces, each with its own schemas and database role. & \stdone \\
FR-15 & \textbf{Sample data.} Provide generated example datasets (a coaching fee register, kirana shop sales, a hostel mess register) so that the tool can be demonstrated without private data. & \stdone \\

\paragraph{Import and type inference (FR-1, FR-2).}
\Cref{fig:import} shows the import screen. Raw cells are first stored as text in the source schema \code{ws\_\textless id\textgreater\_src}, so nothing is lost if a guess is wrong. Type inference then runs in SQL: for each column the system counts how many values succeed under each candidate cast, using helper functions such as \code{qlens.try\_date}, and picks the narrowest type for which every non-empty value succeeds. Because Indian spreadsheets commonly write dates day-first, \code{try\_date} tries \code{DD/MM/YYYY} before any month-first reading.

\screenshot{import-dark}{Importing a sheet: inferred types and preview}{fig:import}

\paragraph{Discovery and cleanup (FR-3 to FR-5).}
Dependency checking is expressed as a grouped aggregate: a dependency \fd{X}{A} holds if no group of rows sharing the same \code{X} contains more than one distinct value of \code{A}. The PL/pgSQL functions \code{qlens.check\_fd} and \code{qlens.is\_unique} implement this test, and a search over small determinant sets uses them to find candidate keys and minimal dependencies. For the 3,000-row fee register the whole analysis takes about 0.3 s. The cleanup step exists because real data violates the dependencies it ought to satisfy; the planted errors in the sample register (eight rows with spelling variants of a student name, and five rows carrying a superseded phone number for Mr.\ Gupta) are exactly the cases that stop a clean dependency from being discovered.

\paragraph{Proposal and apply (FR-6, FR-7).}
The proposal uses the synthesis algorithm of Bernstein~\cite{bernstein1976}, described in the design chapter, which guarantees a dependency-preserving, lossless-join decomposition in third normal form. The apply step re-checks that guarantee against the real rows rather than trusting the algorithm: it compares the cleaned source with the join of the new tables using \code{EXCEPT ALL} in both directions, so that duplicate rows are counted and not collapsed.

Security deserves a short justification because the product, by design, lets a user type SQL. A single check in the application (for example rejecting statements that begin with anything other than \code{SELECT}) is easy to bypass with a comment, a semicolon or a function call that writes. QLens therefore enforces the restriction at several layers that fail independently: the database role cannot write outside its own schemas, the transaction is declared \code{READ ONLY}, a time limit stops an accidental cross join, and the result is truncated at 1,000 rows before it is serialised. The design follows the usual advice for multi-tenant PostgreSQL and the privilege model described in the PostgreSQL documentation~\cite{postgres18docs}.

\subsection{Detailed use case: normalise the fee register}

\noindent\textbf{Actor:} owner of a coaching centre.\quad \textbf{Precondition:} logged in, workspace created, the 3,000-row fee register imported (UC-2).\quad \textbf{Postcondition:} the workspace holds four related 3NF tables whose join equals the cleaned register.

\begin{enumerate}
  \item The owner opens the Analyze screen and starts the analysis. The system computes dependencies and keys in SQL (about 0.3 s) and lists the issues found.
  \item The system reports the near-duplicate groups. Eight rows contain spelling variants of one student name; the owner confirms the suggested canonical spelling.
  \item The system reports that one student, Mr.\ Gupta, has two different phone numbers; five rows hold the old number. The owner selects the current number and the system rewrites those rows, writing one entry per change to \tbl{dataset\_fixes}.
  \item The system re-runs discovery on the cleaned data. Dependencies that were previously blocked now hold: \fd{student\_name}{student\_phone, batch}, \fd{batch}{teacher} and \fd{teacher}{teacher\_phone}.
  \item The system computes the minimal cover, synthesises the relations and displays the proposal:
  \begin{itemize}
    \item \tbl{students}(\code{id}, \code{student\_name}, \code{student\_phone}, \code{batch\_id});
    \item \tbl{batches}(\code{id}, \code{batch}, \code{teacher\_id});
    \item \tbl{teachers}(\code{id}, \code{teacher}, \code{teacher\_phone});
    \item \tbl{fee\_register}(\code{id}, \code{student\_id}, \code{month}, \code{fee\_paid}, \code{payment\_mode}) with \code{UNIQUE}(\code{student\_id}, \code{month}).
  \end{itemize}
  \item The owner reviews the generated DDL and the diagram and chooses \emph{Apply}.
  \item In a single transaction the system creates the four tables, inserts the rows, and runs the \code{EXCEPT ALL} comparison between the join of the new tables and the cleaned source. If both differences are empty the transaction commits.
  \item If the comparison finds any difference, the transaction is rolled back, the workspace is left unchanged, and the owner is told which rows differ.
\end{enumerate}

\noindent\textbf{Alternative flows:} at step 2 or 3 the owner may reject a suggestion, in which case the dependency stays unsatisfied and the proposal keeps the affected attributes together in a wider relation; at step 6 the owner may rename tables or columns, which only changes the generated DDL.

\section{Other Software Engineering Methodologies}
\label{sec:methodology}

\subsection{Iterative, test-driven development}

The project was built in short iterations, each delivering one vertical slice that could be run and shown: first the database and migrations, then authentication and workspaces, then import, then analysis, then the proposal. Within an iteration the work was divided into small tasks. For each task a failing test was written first, the minimum code was added to make it pass, and the result was reviewed against the written specification before the next task started. Review caught real defects, for example in the handling of connection commits and in how generated names collided, and each such defect was turned into a regression test (\code{test\_conn\_commit.py}, \code{test\_naming.py}). The sequence of iterations kept the riskiest part, the algebra of dependencies and the claim of losslessness, in the earliest tested code.

\subsection{Migration-based schema management}

The database schema is not edited by hand. It is defined by numbered SQL files that a runner applies in order and records in a version table: \code{001\_schema.sql} (tables and constraints), \code{002\_logic.sql} (triggers, helper functions, the \code{check\_fd} and \code{is\_unique} functions), \code{003\_ingest.sql} (staging and type inference) and \code{004\_analysis.sql} (analysis support and views). A fresh clone therefore reaches exactly the same schema as the developer's machine, and \code{test\_migrate.py} verifies that running the migrations twice is harmless.

\paragraph{Results.} At the time of writing, 212 backend tests pass in the latest full run, including the property-based tests of third normal form and losslessness. Tests for the apply step, the query sandbox interface and the later features (performance lab, visualiser, assistant) are written together with those features and are not yet part of the totals.
